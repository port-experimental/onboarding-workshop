## Key Concepts

### Scorecards are Blueprints

In the current Port model, scorecards are **first-class blueprints**. When you create a scorecard, Port creates three related blueprints behind the scenes:

| Blueprint | Description |
|-----------|-------------|
| `Scorecard` | The scorecard definition — levels, rules, and target blueprint |
| `Scorecard Rule` | Each rule is its own entity, linked to its Scorecard |
| `Scorecard Rule Result` | Per-entity rule evaluation results, auto-generated by Port |

This means scorecard data is queryable like any other catalog data — you can build dashboards, run automations, and set up filters on scorecard entities.

### Scorecard JSON Schema

A scorecard is defined with this structure:

```json
{
  "identifier": "Ownership",
  "title": "Ownership",
  "blueprint": "service",
  "levels": [
    { "color": "paleBlue", "title": "Basic" },
    { "color": "bronze", "title": "Bronze" },
    { "color": "silver", "title": "Silver" },
    { "color": "gold", "title": "Gold" }
  ],
  "filter": {
    "combinator": "and",
    "conditions": [
      { "operator": "isNotEmpty", "property": "$team" }
    ]
  },
  "rules": [
    {
      "identifier": "has-resp-team",
      "title": "Has responsible team",
      "description": "The service has a designated responsible team",
      "level": "Bronze",
      "query": {
        "combinator": "and",
        "conditions": [
          { "operator": "isNotEmpty", "property": "$team" }
        ]
      }
    }
  ]
}
```

Key fields:
- `blueprint` — the identifier of the blueprint this scorecard measures
- `levels` — ordered quality tiers from lowest to highest
- `filter` — optional: which entities this scorecard evaluates (omit to apply to all)
- `rules` — the quality checks; each rule belongs to a level

### How Levels Work

An entity reaches a level when it passes **all rules at that level AND all lower levels**:

- **Basic**: default — no rules required
- **Bronze**: pass all Bronze rules (and Basic, which has no rules)
- **Silver**: pass all Bronze rules + all Silver rules
- **Gold**: pass all Bronze + Silver + Gold rules

### Rule Operators

| Operator | Use Case | Example |
|----------|----------|---------|
| `isNotEmpty` | Required field has a value | `description isNotEmpty` |
| `isEmpty` | Field has no value | `deprecated isEmpty` |
| `=` / `!=` | Exact match / not equal | `language = "Python"` |
| `>` / `<` / `>=` / `<=` | Numeric comparison | `coverage > 80` |
| `contains` | String contains substring | `description contains "API"` |
| `in` | Value is one of a set | `status in ["active", "healthy"]` |

> **Coming from the old Scorecard model?** Before mid-2025, scorecards were configured as tabs inside each blueprint's settings — not as standalone blueprints. In the new model:
> - Scorecards have their own entries in the Builder (as `Scorecard`, `Scorecard Rule`, `Scorecard Rule Result` blueprints)
> - The `blueprint` field in the scorecard JSON specifies which blueprint is measured
> - Score results are auto-generated `Scorecard Rule Result` entities you can query and visualize
>
> If your account is still on the old tab-based model, the Scorecards tab experience is the same but the underlying storage model differs. Check [docs.port.io/promote-scorecards/](https://docs.port.io/promote-scorecards/) for migration guidance.

## Hands-On Exercise: Production Readiness Scorecard

Let's create a Production Readiness scorecard for TechCorp services.

### Step 1: Access the Scorecards configuration

1. Navigate to **Builder** → **Data Model**
2. Find the **Service** blueprint
3. Click on the **Scorecards** tab
4. Click **+ New scorecard**

### Step 2: Create the scorecard

Paste this JSON into the scorecard editor:

```json
{
  "identifier": "production_readiness",
  "title": "Production Readiness",
  "blueprint": "service",
  "levels": [
    { "color": "paleBlue", "title": "Basic" },
    { "color": "bronze", "title": "Bronze" },
    { "color": "silver", "title": "Silver" },
    { "color": "gold", "title": "Gold" }
  ],
  "rules": [
    {
      "identifier": "has_description",
      "title": "Has Description",
      "description": "Service has a non-empty description",
      "level": "Bronze",
      "query": {
        "combinator": "and",
        "conditions": [
          { "operator": "isNotEmpty", "property": "description" }
        ]
      }
    },
    {
      "identifier": "uses_supported_language",
      "title": "Uses Supported Language",
      "description": "Service uses a language on the approved list",
      "level": "Silver",
      "query": {
        "combinator": "or",
        "conditions": [
          { "operator": "=", "property": "language", "value": "Python" },
          { "operator": "=", "property": "language", "value": "JavaScript" },
          { "operator": "=", "property": "language", "value": "Java" }
        ]
      }
    },
    {
      "identifier": "is_active",
      "title": "Not Archived",
      "description": "Service is not in an archived state",
      "level": "Gold",
      "query": {
        "combinator": "and",
        "conditions": [
          { "operator": "=", "property": "archived", "value": false }
        ]
      }
    }
  ]
}
```

### Step 3: Save and verify

After saving:
1. Navigate to **Catalog → Services**
2. Each service should now display a scorecard level badge (Basic, Bronze, Silver, or Gold)
3. Click a service to see which rules it passes and fails

### Step 4: Understand a service's level

For a service with:
- ✅ Description is not empty (Bronze rule passes)
- ✅ Language is Python (Silver rule passes)
- ❌ `archived` is `true` (Gold rule fails)

**Result**: Silver — passed all Bronze + Silver rules, failed Gold.

## Using the `filter` Field

The `filter` field scopes which entities a scorecard evaluates. Without a filter, the scorecard applies to all entities of the target blueprint.

Example — only evaluate services that belong to a team:

```json
{
  "filter": {
    "combinator": "and",
    "conditions": [
      { "operator": "isNotEmpty", "property": "$team" }
    ]
  }
}
```

This is useful when some entities are exempt from a quality framework (e.g., deprecated or experimental services).

## Integrating Scorecards with Automations

Because scorecard results are now first-class entities, you can trigger automations when a scorecard level changes.

Example: the automation from Module 6 that notifies on a scorecard level drop:

```json
{
  "identifier": "notify_scorecard_drop",
  "title": "Notify on Scorecard Level Drop",
  "trigger": {
    "type": "automation",
    "event": {
      "type": "ENTITY_UPDATED",
      "blueprintIdentifier": "service"
    },
    "condition": {
      "type": "JQ",
      "expressions": [
        ".diff.before.scorecards.production_readiness.level == \"Gold\"",
        ".diff.after.scorecards.production_readiness.level != \"Gold\""
      ],
      "combinator": "and"
    }
  },
  "invocationMethod": {
    "type": "WEBHOOK",
    "url": "https://hooks.example.com/port-alerts"
  },
  "publish": true
}
```

## Scorecard Design Best Practices

### Make levels progressive and actionable

Each level should be meaningfully harder than the previous, and every rule should be something a team can actually fix:

- **Bronze**: Basic hygiene (has a description, has an owner)
- **Silver**: Operational readiness (has a runbook, monitored, uses approved stack)
- **Gold**: Excellence (has SLO defined, test coverage > 80%, no open critical vulnerabilities)

### Use filters to scope appropriately

Don't apply Gold-level quality standards to internal tooling or experimental services. Use `filter` to limit scorecards to the relevant population.

### Involve teams in scorecard design

Scorecards that surprise teams create friction. Share the rules in advance and give teams time to improve before enforcement.

## Common Issues & Solutions

**Problem**: All services show "Basic" level even after saving the scorecard  
**Solution**: Check that the rule's `property` identifier matches the blueprint property exactly (case-sensitive). Use Builder → Data Model → Service to verify property identifiers.

**Problem**: Rule evaluates incorrectly for boolean properties  
**Solution**: Use `{ "operator": "=", "value": false }` not `{ "operator": "isEmpty" }` for boolean properties — `isEmpty` checks for null/undefined, not `false`.

**Problem**: Scorecard doesn't appear in the Catalog  
**Solution**: The Scorecards-as-Blueprints rollout is gradual. If you don't see the Scorecard blueprint in Builder, the feature may not yet be enabled for your account. Check [docs.port.io/promote-scorecards/](https://docs.port.io/promote-scorecards/) for rollout status.

**Problem**: `filter` field causes no entities to be evaluated  
**Solution**: Verify your filter condition is correct. An overly restrictive filter (e.g., checking a property that no entity has set) will exclude all entities.
